## Supported environments

| Environment | Scope |
| --- | --- |
| Linux AMD64 + PostgreSQL 18 | Release build and validation target. The pinned PostgreSQL build and optional pg_textsearch version are in [environment.lock.json](../docker/environment.lock.json). |
| macOS ARM64 + PostgreSQL 18 | Local development with the isolated runner. It does not provide local BM25 or recovery suites. |
| Other operating systems, CPU architectures, or PostgreSQL majors | No repository validation entry point is provided. |

Native FTS requires a UTF8 database and a matching pg_charabia library. It does not require pg_textsearch. BM25 also requires the pinned pg_textsearch build, its dynamic dependencies, and preload setup before server startup.

The project version and dependencies come from [Cargo.toml](../Cargo.toml) and [Cargo.lock](../Cargo.lock). Resources are embedded and identified in [resources/manifest.json](../resources/manifest.json). There are no runtime data downloads.

## Build from source

Source builds and locally generated release archives remain available alongside the [v0.4.2 release package](https://github.com/hhkbble/pg_charabia/releases/tag/v0.4.2).

Use the prerequisites and commands in [Build and test](development.md#build-and-test). The isolated runners build and stage the extension in a private PostgreSQL cluster. They do not install files into the target PostgreSQL distribution. A targeted build is not full release acceptance.

To generate a verified Linux AMD64 archive, follow [Release acceptance and packaging](development.md#release-acceptance-and-packaging). Then use the installation procedure below on the target host. Keep source and rebuild materials with the package.

## Download and install

Open the [v0.4.2 release page](https://github.com/hhkbble/pg_charabia/releases/tag/v0.4.2). Download the complete Linux AMD64 `.tar.gz` asset and its matching `.tar.gz.sha256` file. GitHub's automatic source archives do not contain the installed extension binary.

On the Linux AMD64 target host, put both downloaded files in the same directory. Set `RELEASE_ARCHIVE` to the downloaded archive filename, without a directory prefix. Verify the archive before extracting it:

```sh
: "${RELEASE_ARCHIVE:?Set RELEASE_ARCHIVE to the downloaded .tar.gz filename}"
sha256sum --check "$RELEASE_ARCHIVE.sha256"
tar -xzf "$RELEASE_ARCHIVE"
```

Stop if the checksum fails. The archive contains one package root with `delivery-manifest.json`, `SHA256SUMS`, extension files, source, resources, notices, and verification evidence. The binary stays inside this complete package.

Read the manifest's `quality` summary and the [reviewed release warnings](reference.md#reviewed-release-warnings) before adopting the default analysis. The package retains the original failure report and current warnings. Warning counts are separate from quality PASS.

Use the extracted, verified Linux AMD64 package for the installation steps below. The same steps apply to an archive generated by the repository's release procedure.

1. Match the package to the target PostgreSQL major, operating system, CPU architecture, ABI, and dynamic dependencies. Read `delivery-manifest.json` first.
2. On the target host, enter the extracted package root. Set `PG_CONFIG` to that PostgreSQL 18 installation's `pg_config`.
3. Run the inspection commands below. Stop on a checksum, architecture, PostgreSQL version, or dependency mismatch.
4. For an existing 0.4.1 installation, stop PostgreSQL as described in [Upgrade from 0.4.1](#upgrade-from-041) before replacing files.
5. Run the two `install` commands with administrative permissions. They change the target PostgreSQL installation.

```sh
: "${PG_CONFIG:?Set PG_CONFIG to the target PostgreSQL 18 pg_config}"
"$PG_CONFIG" --version
sha256sum --check SHA256SUMS
file extension/pg_charabia.so
ldd extension/pg_charabia.so
install -m 755 extension/pg_charabia.so "$("$PG_CONFIG" --pkglibdir)/pg_charabia.so"
install -m 644 extension/*.control extension/*.sql "$("$PG_CONFIG" --sharedir)/extension/"
```

A macOS library cannot load into Linux PostgreSQL. Keep the complete package, checksums, resource manifest, and dependency notices after installation.

## Fresh installation

Version 0.4.2 keeps the fresh installation baseline introduced in 0.4.0.
It provides no compatibility object names or upgrade from 0.4.0 or 0.3.x.
For a new database, install the complete verified 0.4.2 package, then run:

```text
CREATE EXTENSION pg_charabia;
SELECT extversion AS catalog_version,
       charabia.analysis_info()->>'extension' AS library_version
FROM pg_catalog.pg_extension WHERE extname='pg_charabia';
```

Both versions must be `0.4.2`. Installation creates three configurations:

- `public.charabia_linguistic` uses ordinary language analysis.
- `public.charabia_structured` adds structured recognition and expansion. Select it explicitly.
- `public.charabia` is the default linguistic entry. At installation it has the
  same Parser and mappings as `public.charabia_linguistic`.

The two linguistic configurations are separate PostgreSQL objects. Later mapping
changes are independent. Their shared Dictionary parameters can affect both,
as well as any other configuration that references those Dictionaries. A
Configuration COPY also keeps Dictionary references; create independent
Dictionaries when an application needs independent parameters.

The extension does not change the host's `default_text_search_config`. Pass the
intended configuration explicitly to native FTS, headline, and index expressions.
Extension diagnostic and query defaults use `public.charabia`; see the
[Usage reference](reference.md) for signatures and native-call behavior.

A complete 0.3.x dump is not automatically compatible with the fresh baseline.
Retain the exact old package, source text, application object definitions, and
external rules. If old data is needed, read it in an isolated environment with
that old package, then create the new definitions and reanalyze original text in
the fresh database. This is not an in-place extension upgrade. Validate independent
document IDs, actual GIN/BM25 plans, and original-text headline before opening
traffic. Keep old packages for recovery targets that require their exact library.

## Upgrade from 0.4.1

Version 0.4.2 preserves 0.4.1 SQL signatures, object definitions, dictionary defaults, resources and both analysis modes. The native upgrade changes the extension version without recreating objects. Existing object OIDs, permissions, user configurations, stored vectors and GIN/BM25 indexes remain valid. This upgrade alone needs no vector recomputation or index rebuild. Independent changes to dictionaries or mappings still require the [normal maintenance](#analysis-changes-and-index-maintenance).

1. Verify the complete 0.4.2 package on the matching target. Retain the exact 0.4.1 package and a backup for older recovery targets.
2. Pause application traffic and end old connections. Stop PostgreSQL before replacing the loaded binary. A configuration reload does not replace backend libraries.
3. Install the verified binary, control file, 0.4.2 installation SQL and `pg_charabia--0.4.1--0.4.2.sql` with the [installation commands](#download-and-install). Keep older packages and installation SQL.
4. Restart PostgreSQL with application traffic still paused. Open a new administrative connection and run the following in each database that has pg_charabia 0.4.1:

```sql
ALTER EXTENSION pg_charabia UPDATE TO '0.4.2';
SELECT extversion AS catalog_version,
       charabia.analysis_info()->>'extension' AS library_version
FROM pg_catalog.pg_extension WHERE extname='pg_charabia';
```

Both versions must be `0.4.2`. Validate application queries and index plans, then reconnect applications and reopen traffic. Do not manually edit pg_extension or drop and recreate the extension for this upgrade. The new library reports 0.4.2 before ALTER updates the catalog, so keep traffic paused through that step.

The default Rust heap now uses PG TopMemoryContext storage. Rust ownership and Drop still release individual objects through pfree. PG can retain freed capacity for reuse. This storage survives request resets and is not limited by work_mem. Infallible Rust OOM can still abort a backend and trigger PostgreSQL instance recovery. Allocation costs and memory residency can differ from 0.4.1. This release does not promise performance parity. See [Ownership and errors](architecture.md#ownership-and-errors) for the runtime contract.

## Optional pg_textsearch setup

For BM25, separately install the pg_textsearch build pinned in [environment.lock.json](../docker/environment.lock.json). Add `pg_textsearch` to `shared_preload_libraries`, preserving other required entries, then restart PostgreSQL. pg_charabia installation does not change this parameter. Native FTS users skip this step.

## Schema ownership and permissions

A database superuser runs `CREATE EXTENSION pg_charabia`. Installation reserves the fixed `charabia` schema and all three public configurations listed above. The extension is not relocatable. Conflicting objects cause atomic failure rather than replacement.

If `charabia` already exists, the installer must own it and it must deny untrusted `CREATE` privileges. This includes inherited `CREATE` privileges and inherited authority to grant them. Otherwise, installation fails with `42501`. Installation grants `PUBLIC` schema `USAGE`, revokes `PUBLIC CREATE`, and leaves existing `public` schema permissions unchanged.

Create custom objects in an application-owned schema with normal PostgreSQL permissions. Use schema-qualified names in applications and indexes. Unqualified names require a trusted `search_path`. Names and prefixes do not establish ownership or permission to delete an object.

## Analysis changes and index maintenance

Dictionary parameters, candidate/route sets, segmentation features, whole-word restoration, mappings, chain order, external rules, and resource changes can invalidate old indexed terms. Cache invalidation rebuilds process state, not vectors or indexes. A route/type-ID
change also requires correct new Configuration mappings and affected expression
or index definitions. Replacing a library or rebuilding postings alone does not
repair old numeric mappings. The build/resource fingerprint does not certify user chains or existing indexed data.
An existing Configuration COPY does not automatically gain new mappings or objects added to its source configuration. Changing mappings cannot replace a Configuration's Parser. To change modes, create a Configuration with the intended Parser and update application and index references; do not mix postings from the two modes.

1. Inventory affected configurations, shared Dictionary references, stored vectors, and indexes. Include COPY relationships.
2. Save source text, ordinary object DDL, owners, package/resource identity, and external rules.
3. Pause affected reads/writes and end old transactions and backends before changing analysis or loaded binaries.
4. Apply the change, then recompute/rebuild using the table below. Use the same configuration for document and query analysis.
5. Reprepare queries affected by constant folding. Validate parameterized custom/generic plans separately.
6. Validate expected document IDs, stored values, actual GIN/BM25 plans, and original-text headline before reopening traffic.

| Representation or change | Required action |
| --- | --- |
| Expression GIN on `to_tsvector` | REINDEX reruns the expression and analysis. |
| Ordinary `tsvector` column with GIN | Recompute the column from source text, then maintain its index. REINDEX alone reuses the old vector. |
| Generated `tsvector` column with GIN | Update source values or redefine the expression to trigger recomputation, then maintain the index. |
| BM25, same configuration OID | REINDEX after parameter or mapping changes. |
| Replacement configuration OID or analysis mode | Recreate affected expressions/indexes for the new configuration and recompute stored vectors from original text. For BM25, replace the index or set the new text_config and rebuild. |
| Dictionary rename or schema move | Mappings keep the OID. A name-only change does not itself require reanalysis. |
| Configuration rename or schema move | Native OID references remain. Update BM25's text_config string and REINDEX, or create a replacement index. |

For BM25 name changes, use `ALTER INDEX ... SET (text_config='new_schema.new_name')` and REINDEX. Changing the reloption alone is insufficient. Before dropping a configuration, inspect the BM25 inventory. The pinned upstream version lacks complete configuration dependency protection.

## Backup and recovery

Logical dumps preserve ordinary dictionaries, parameters, mappings, owners, and dependencies, but restored objects receive new OIDs. Prepare roles, schema permissions, installed extensions, and external rules before restore. Validate subsequent ALTER/DROP operations, both modes, shared and independent Dictionary parameters, and original-text headline afterward.

Restore a logical backup into its matching version of the fresh baseline. Default extension members are rebuilt from the installed package. User changes to those members are not saved as independent member definitions. Keep custom settings in ordinary application objects.

Point-in-time recovery (PITR) needs a complete cluster base backup and continuous archived write-ahead log (WAL) through the target. The target cannot precede the backup's earliest consistent point. Retain the following outside the database backup:

- The exact extension package, control/SQL files, dynamic libraries, resource manifest, checksums, English TXT/attribution, and source/rebuild materials for the target time.
- Matching pg_textsearch files and preload setup when BM25 is used.
- External synonym or other dictionary rule files, plus required locale/OS dependencies and server/restore configuration.

WAL does not restore installation directories or replay later configuration-file edits. Embedded resources travel with their exact library. Do not substitute an unverified newer package for the target package.

Prefer a named restore point after analysis maintenance finishes. If the target falls between a parameter change and its rebuilds, keep traffic closed and finish maintenance. Physical replay does not rerun historical SQL or text analysis. A consistent restore cannot fix a semantic mismatch already present at the target.

After recovery, validate LSN/timeline, parameters, mappings, cold Dictionary initialization, loaded library hash, stored vectors, independent candidates, actual GIN/BM25 plans, and original-text headline in both modes. A physical 0.3.x recovery target still needs its exact old package; the current package is not a replacement for that package. Changes to binaries, redo components, or index formats require a matching recovery rehearsal. See [PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html) and the [technical recovery boundary](architecture.md#persistent-state-and-recovery).
